# サーバー側の日記生成（Issue #8）

ブロックのINSERT/UPDATE/DELETEをDBで検知し、所有者と生活日ごとの永続ジョブへまとめる。生成ワーカーがDBから最新の出来事（event）を読み、該当日だけを全文再生成・保存する。画像だけの追加・削除・並び替えも対象。原ブロックは生成処理で変更しない。

## 変更と生成の流れ

1. ブロックとジョブを同一トランザクションで保存する。画面の直接保存、REST API、MCP、capture系を共通で捕捉する。
2. 最後の変更から5秒待ち、同日の連続変更をまとめる。開始待ちの期日は最初の変更から最大30秒。ワーカーは10秒間隔で呼ばれるため、このほかにポーリング間隔と、実行中のLLM応答・再試行時間が加わる。
3. 同じ日では1つだけジョブをclaimする。生成中の変更は世代を増やすだけで並列生成しない。
4. 保存時に世代・生成入力・モデル/プロンプト設定・生活日境界・既存日記の状態を原子的に再照合する。変わっていれば古い結果を破棄し、最新状態の次の1回へまとめる。更新が止まれば最新状態へ収束する。
5. 日付移動では移動元/移動先を処理する。eventから別カテゴリへの変更や削除も反映する。対象日のeventが0件ならLLMは呼ばず、生成済み本文とsummaryを空にする。直前版は履歴へ保全する。他の日は変更しない。

原ブロックの本文、日時、画像、所属先、タグはワーカーから更新しない。生成済み日記の文章は、その日全体の再生成で変更される通常動作。手修正を理由とする毎回の承認待ちは設けないが、生成中に入った編集は古い結果で上書きしない。採点設定が有効で規範が設定されていれば、日記生成後に同じワーカー内で従来の採点も行いscore/score_detailsを保存する。採点OFFなら採点LLMを呼ばず、採点失敗時は従来と同じく日記を保存して既存の採点値を保持する。時刻推測、OCR、画像の内容解析は実行しない。

## 永続性・上限・所有者分離

- 待機ジョブはPostgreSQLの `diary_generation_jobs` に残る。`SKIP LOCKED`によるclaimと180秒のlease、ランダムなトークンによる保存制御を使う。古いleaseのワーカーは保存できない。
- 同じ入力を再処理しても保存済み指紋が一致すればLLMを呼ばない。同値PATCHや日記に関係しないフィールドの更新はジョブを作らない。冪等POSTの再送もブロックを追加しないのでジョブが増えない。
- 1世代の試行は最大3回。失敗は10×試行回数²秒後（上限120秒）に再試行する。生成待ち中の更新で最新世代へ切り替わる。公開するエラーは固定コードとし、モデル応答・秘密鍵・本文をエラーログに出さない。
- 既定の上限は所有者・対象日ごとにUTCの1日20試行。1試行につきLLMは日記が最大2回、採点ON時は採点も最大2回（出力検証の再試行）、各リクエスト30秒、出力上限4096トークン。出力上限で切れた応答は保存せず失敗として扱う。課金額そのものの固定上限ではない。上限到達は `daily_budget` として停止し、時間窓の更新後に次の変更または明示的な再試行で再開する。
- ネットワーク終了後にプロバイダー側で課金が成立したか不明な場合までLLM課金の厳密な一度性は保証しない。保存の重複・古い結果の上書きはDBで防ぐ。
- ジョブ・履歴・制御テーブルと内部RPCはservice_role専用。ブラウザーは `auth.uid()` で本人に限定した状態取得・再生成依頼RPCだけを使う。REST APIは既存のAPIトークンで得た所有者を使う。
- モデル・APIキーの取得も所有者で絞る。割り当てたモデルやキーが利用できない場合は、別のモデルへ黙って切り替えず失敗として扱う。

## APIと画面

OpenAPIは1.2.0。ブロック保存の成功と日記生成の完了を分ける。

- `GET /entries/{date}/generation`: `active`, `status`, `generation`, `saved_generation`, `completed_at`, `error_code` を返す。
- `POST /entries/{date}/regenerate`: 本人のその日の再生成・再試行を202で受け付ける。本文は送らない。既に待機/実行中ならまとめる。停止中は409。
- `GET /entries/{date}`: 保存済み本文を返し、blocksはワーカー/画面と同じ生活日範囲で取得する。旧APIでentry_idが暦日に割り当てられたブロックも原データを変更せず読み戻せる。生成待ちの間は前回の本文で、生成完了後に更新される。
- ブラウザー用RPC: `diary_generation_status(p_date)`、`request_diary_generation(p_date)`。画面は3秒間隔で状態を読み、変化時に対象日を再取得する。画面が非表示の間はポーリングを控える。
- 画面はLLMを呼ばず、日記も直接保存しない。手動再生成も同じジョブへ依頼する。旧 `format-entries` のHTTP入口は410を返して、古いキャッシュのクライアントによる時刻変更・二重生成を止める。日記生成の共通処理は `format-entries/diary.ts` へ分離した。

以前の「画像だけPATCHでは整形済み日記が変わらない」という契約は、有効化後は「原ブロックは保全し、その生活日の日記は非同期で更新する」へ変更する。既存の同期APIテストは保存時の原ブロック保全、新しいジョブ試験は後続の日記更新をそれぞれ検証する。

## 既存のDrizzleマイグレーションを適用する

2026-10-29のLovable適用は `42P07: diary_generation_control already exists` で停止した。その後の独立したSELECTでは新規3テーブルは存在せず、`drizzle.__drizzle_migrations` は0000の1行のみだった。Lovableの実行記録には、既に0001がある状態で、そのSQLを `lov_database--migration(name, query)` に渡した操作がある。未適用の0001に加えて同じSQLを新規作成して実行した可能性が高い。ツール内部の実行ログは取得できず、原因の断定はしていない。

架空DBで、実Drizzle migratorに同じSQLの未適用ファイルを2つ渡すと、同じ42P07と全体ロールバックを再現できる。既存の0001だけなら適用成功し、再実行は何も変更しない。本番復旧ではSQLを `IF NOT EXISTS` に変更したり、履歴を手作業で適用済みにしたりせず、既存ファイルの適用経路を使う。

1. ファイル側の `_journal.json` と `.sql` を確認する。現在の想定は0000/0001の2件。失敗時に重複0002等が残っていれば、その内容・ハッシュとDB未適用を確認するまで実行しない。正規0001や適用済み0000を削除・再作成しない。
2. SELECTでDB履歴のhash/created_atをファイル側と照合する。未反映時の想定は0000だけ（created_at `1793199307320`、SHA-256 `1d6109559b09025ba5a0dd4303d7aaf7e6192087e63c1cb2d8e25fc2b765f81f`）、新規3テーブルと新規RPCは未作成。部分的な作成や予期しない履歴があれば停止する。既に0001が適用済みならSQLを再送せず、ハッシュと停止状態を検証する。
3. Cloudが提供する `LOVABLE_DB_MIGRATION_URL` を秘密のまま利用できる環境で、プロジェクトルートから **`npm run db:migrate`** を実行する（実体: `drizzle-kit migrate --config=drizzle.config.ts`）。依存関係は既存ロックファイルに従って用意する。これは適用履歴から未適用ファイルだけを選び、SQLと履歴を同じトランザクションで反映する。接続URLを表示・コマンド引数へ展開・Git保存しない。
4. 新しいSQLの生成、`drizzle-kit generate` / `push`、`lov_database--migration` へのSQL再投入は行わない。Cloudで既存ファイルを適用する正式な機能がある場合はそれでもよいが、新規ファイルを作らないことを確認する。接続URLや適用権限が提供されない場合は、その不足を報告して停止する。
5. 適用後、別のSELECTで0000/0001の履歴と各SQLのハッシュ、3テーブル・RPC・RLS/権限、および `enabled=false, all_users=false, allowed_user_ids={}` を確認してから関数配備へ進む。ジョブ・履歴は0件であることも確認する。失敗した場合は再試行や履歴修正をせず、ロールバック後の状態を読み取って報告する。

DB反映前の型自動生成では、未作成RPCが `src/integrations/supabase/types.ts` から消えることがある。今回必要な `diary_generation_status` / `request_diary_generation` の型を失った状態で画面を公開しない。マイグレーション成功後に型を再生成し、`npx tsc -b --force` とビルドを確認する。

Drizzleの既存ファイル適用と履歴管理は[公式のmigrate手順](https://orm.drizzle.team/docs/drizzle-kit-migrate)に従う。この手順と追加テストは本番への適用成功を示すものではない。

## 停止・復元

- 運用停止は `diary_generation_control.enabled=false`。新規claimと進行中ジョブの保存を止める。既に送信したLLMリクエストの費用は取り消せない。必要なら `cron.unschedule('flowlog-diary-worker')` で定期実行も止める。
- 直前の日記は `diary_generation_history` に直近5版を保全する。原ブロックには復元操作を行わない。
- 本人が指定した1件の復元は、停止後に履歴と現在の日時を読み、service_role専用 `restore_diary_generation(p_user_id,p_date,p_history_id,p_expected_updated_at)` を使う。所有者/日付/履歴IDと現在のupdated_atが一致しなければ復元しない。本人の新しい編集を盲目的に戻さない。
- ワーカーや画面を旧版へ戻す場合も、旧クライアントと旧format-entriesによる自動書き込みを再開しないことを確認する。ジョブ・履歴は消さず、再配備で整合を取り直す。
