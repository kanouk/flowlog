## コピーと秘密値

採点のモデルは利用者の指定で日記と同じものに設定した。この承認済みの設定差分は非公開の照合用overrideとして記録し、元のsnapshotを変更しない。

本人分のコピーは復元用の全アカウントexportと分け、非公開の `.migration-backups/` に保管する。全アカウントの復元試験、最終同期、元DBの書き込み停止は未実施。匿名等の別IDは自動統合していない。

画像URLはmanifestに一致するものだけを隔離WorkerのURLへ置き換えた。既存日記の文章は書き換えず、URLだけを変換した。初回の基本版ではキー参照を解除していたが、その後の全機能移植でAIキー3件・外部トークン1件とモデルの参照関係を移した。取得結果は暗号化した状態で搬出し、秘密値はstaging専用のAES-GCM鍵で暗号化してD1へ保存する。ブラウザへは安全なメタデータとマスク表示だけを返す。キー原文をログ・Git・Issueへ出さない。

新規画像の保存先はR2。Gyazoトークンは保持する。承認された架空画像1枚のアップロード・削除を終え、通常の外部書き込み停止とR2保存へ戻した。本番APIトークン・旧session・旧パスワードhash・短命のOAuthコードは取り込んでいない。隔離MCP/APIの試験には検証用に発行したトークンを使い、終了後に削除する。

## 生成範囲と配備範囲

Workerのpreview URLとR2の公開用URLは無効。記録・画像・認証の応答はprivate/no-store。画面は同一ホストのフォントと圧縮コードを使用する。ルートの紹介ページとログイン画面は公開し、個人データは本人認証を要求する。

回復用Cronは専用Workerに1分間隔で登録し、専用Queueだけを送受信する。導入時は停止していたが、利用者の依頼に基づき、2026-10-29 22:27 JSTから新規記録だけの自動生成を有効にした。従来の試験用allowlistは空のまま。取り込みで過去の日記ジョブを一斉作成しない。承認されたGyazo架空画像試験の終了後、外部サービスの画像更新・削除とメール送信は停止している。

Lovable側の日記SQL・関数・pg_cron/pg_net/Vault・新フロントの配備は凍結したまま。`flowlog.jp`や既存サイトのroute・DNS・ネームサーバーは変更しない。

## 新しく追加する記録だけの自動生成

有効化時点の既存entryと、既存ブロックが属する生活日を、DBの同じトランザクションで保護対象へ登録した。その後にDBへ追加したブロックだけを記録し、「出来事」になったものを生成入力へ使う。利用者が指定できるcreated_atで新旧を判定しない。過去日記のある日へ新しい出来事を追加しても、その日の自動生成や手動の再生成依頼は拒否する。古いブロックを編集・移動しても生成を開始せず、新しい日へ移してもAIの入力には含めない。

新しい出来事の編集・日付移動・削除も同じ範囲で反映する。最後の出来事を削除した場合に空にするのは、その新しい日の生成結果だけ。生成中の入力変更・手編集・設定変更を検出し、古い結果で上書きしない。日記整形の機能設定をOFFにすれば生成を止められる。所有者全体でUTC日20試行、最大3回の試行という上限は維持する。

`new-record-generation.py enable` はアカウントと専用リソースを確認し、最初の有効化時に保護対象を固定する。`disable` は生成だけを止め、保護対象と最初の境界を保持する。再度enableしても過去を取り込んだり、新しい保護境界に置き換えたりしない。停止中に追加した記録も、再開後に自動で取り込まない。

`verify-live-new-records.mjs` は未使用の架空日付だけへ記録を追加し、明示的な生成依頼をせず、Queue → 指定Gemini → 日記・採点の保存 → 画面の更新表示を確認した。コピーした日記の再生成依頼は拒否された。後片付けでは試験日だけを対象から外してから架空記録を削除し、生成の再実行を防ぐ。本人の新しい記録や過去の記録には触れない。Worker/D1/R2のローカル結合試験は172項目が成功した。

## 追加した実接続試験

`verify-live-summary.mjs` は未使用の架空日付に作ったブロックだけで、Firecrawl取得・指定モデルの要約・保存・読み戻しを確認し、作成した記録を片付ける。`verify-live-integrations.mjs` は4モデルの参照、Raindropの実GETによるdry_run、画像設定、検証用OAuth、MCP全14操作を確認する。MCPで使う日付に既存entryがあれば書き込み試験を停止する。外部のOAuth戻り先へコードを送らず、実クライアントも変更しない。

`verify-live-gyazo.mjs` は利用者が承認した架空画像1枚だけの試験用。通常は停止し、必要なときだけ画像ハッシュと10分以内の期限を検証Workerへ設定する。削除は同じ試験のアップロードで取得したIDだけに限定する。試験後は許可を解除してR2へ戻し、再実行で既存画像を削除しない。

## 再開と検証

```sh
npm ci --legacy-peer-deps
npm run port:functions
npm run typecheck:worker
npx tsc --noEmit -p tsconfig.app.json
npm test
npm run test:worker
npm run lint
npm run build:staging
python3 scripts/cloudflare/staging.py deploy
```

生成された移植コードへの修正は再生成で消えるため、実行環境の変更は `port-functions.mjs` に記録する。`worker/test-entry.ts` はローカル結合試験専用で、配備設定から参照しない。配備ガードは専用ブランチ・対象アカウント・Worker/D1/R2/Queue名・入口・Cronを照合し、本番やDNSの操作を含めない。

D1の追加schemaは `staging.py migrate-functions` で適用済みファイルのhashを確認して進める。適用済みSQLを編集して再実行せず、新しい番号のmigrationを追加する。秘密値・リソース識別子を含む設定はローカルのGit除外対象とする。

実環境の確認には `operator-session.py` で期限付きQA sessionを作り、`verify-staging.mjs` と `verify-ui.mjs` を使う。本人のパスワードや既存sessionを初期化しない。試験は架空日付が未使用か確認し、作成したIDの記録だけを削除する。終了後は `operator-session.py remove` でそのQA sessionだけを削除する。初回設定リンクの再発行は通常の試験に含めない。

`rehearsal-gate.py` と `verify-live-diary.mjs` は、初期の停止状態から架空の1日だけを一時許可する旧試験用。現在の新規記録モードが有効な状態では使わない。既に別の運用設定があれば上書きせず停止する。終了時に元のcontrolへ戻す。本人の日記を試験対象に使わない。

GitHub Actionsは手動staging専用workflowを用意したが、未push・Secrets未設定・未実行。正本化は後続作業である。既存依存の監査指摘、本番バックアップの復元、障害通知、実クライアント再接続、本人による受け入れは本番切り替え前の残件として管理する。
